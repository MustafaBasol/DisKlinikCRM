## 5. Existing report/export architecture

The existing export foundation (US-07.3-P1) is a synchronous, server-owned, allow-listed pipeline:

```
Reports.tsx (page)
  -> ReportExportControls.tsx (Export Excel / Export PDF / Print buttons)
    -> reportExportApi.ts: downloadReportExport(reportKey, format, filters, locale)
      -> GET /api/reports/export/:reportKey  (reportExport.ts)
         1. getReportDefinition(reportKey)            — allow-list lookup (Map-based)
         2. format validated against SUPPORTED_EXPORT_FORMATS
         3. isRoleAllowedForReport(user, definition.allowedRoles)
         4. definition.parseFilters(query)             — typed, validated filters
         5. validateAndGetClinicIdScope(user, clinicId, res) — SAME primitive as the JSON report
         6. definition.loadRows({ scope, filters, limit: maxSyncRows + 1 }) — SAME data loader as the JSON report
         7. exceedsSyncRowLimit(rows.length, maxSyncRows) — reject 413, never silently truncate
         8. buildReportExportWorkbookBuffer(...) | buildReportExportPdfBuffer(...)
         9. buildReportExportFilename(...)              — server-derived filename only
        10. recordReportExportAudit(...)                — PII-gated AuditLog write
        11. res.send(buffer) with Content-Type / Content-Disposition / X-Content-Type-Options: nosniff
```

Key architectural properties already established and reused as-is by this proposal:

- **Single allow-listed registry** (`REPORT_DEFINITIONS_MAP`, a `Map` — not a plain object — specifically to fail closed against `__proto__`/`constructor` key confusion).
- **Data-loader reuse**: the export never re-implements a query; it calls the exact same loader function the on-screen JSON report uses, so exported rows can never drift from what the user sees on screen.
- **Authorization reuse**: `isRoleAllowedForReport` mirrors `authorize()`'s canonical-role-or-raw-role check outside the static middleware factory pattern; `validateAndGetClinicIdScope` is the same clinic-scope primitive used throughout the codebase (`server/src/utils/clinicScope.ts`).
- **Thin, authorization-free renderers**: both `pdfBuilder.ts` and `xlsxBuilder.ts` accept already-authorized, already-scoped, already-typed rows and return bytes — no auth, no scope resolution, no DB access inside either renderer.
- **Explicit, closed row cap**: `maxSyncRows` (2000 for `revenue-by-period`) is enforced by rejecting with `ROW_LIMIT_EXCEEDED`, never by truncating.
- **Formula-injection defense**: `neutralizeFormulaInjection` (OWASP CSV/Excel formula-injection mitigation — leading `'` on any text cell starting with `=`, `+`, `-`, `@`) is applied to every text cell in both XLSX and PDF renderers. Numeric/currency/date/boolean columns are never routed through this function, so a legitimate negative number is never turned into neutralized text.
- **PII/audit decision is a pure function of one field**: `shouldAuditReportExport` returns `definition.pii === true`; `revenue-by-period` is `pii: false` (aggregate period/revenue/count rows only, no patient-level data), but the audit call is still made unconditionally on both the success and failure paths — the pure-function gate inside `recordReportExportAudit` is what actually decides whether a row is written.
- **Filename safety**: `buildReportExportFilename` derives the filename only from the server-controlled `filenamePrefix` and the generation timestamp — never from a client-supplied or free-text value.
- **Synchronous, single-process execution**: everything above runs in the request/response lifecycle of the existing Express API process — no queue, no worker, no object storage.

**`pdfkit` 0.19.1** (`server/node_modules/pdfkit/README.md`):
- Ships an **SVG path-data parser and native vector-drawing API**: `doc.path('M 250,75 L 323,301 131,161 369,161 177,301 z')` plus primitive methods (`rect`, `circle`, `moveTo`/`lineTo`/`bezierCurveTo`, fill/stroke, `even-odd` fill rule). This is a **path-data mini-language and drawing primitive set**, not a full arbitrary-SVG-document renderer (no `<image>`, gradients-from-file, external references, or CSS).
- Supports raster image embedding via `doc.image(...)`: **"Supports JPEG and PNG files (including indexed PNGs, and PNGs with transparency)."** This requires the caller to already have PNG/JPEG bytes — pdfkit itself does not rasterize anything to produce those bytes.
- Already used by `pdfBuilder.ts` and (per its own doc comment) `treatmentProposalPdf.ts` with the bundled `NotoSans-Regular.ttf` / `NotoSans-Bold.ttf` fonts at `server/src/assets/fonts/` (confirmed present on disk, ~620KB/~631KB, plus `NotoSans-OFL.txt` license file). Noto Sans has full Latin Extended-A/B glyph coverage, which covers Turkish (ç, ğ, ı, İ, ö, ş, ü), French (é, è, ê, ë, à, ç, œ), and German (ä, ö, ü, ß) diacritics — already proven in production by the existing table renderer and by `treatmentProposalPdf.ts`.

**`exceljs` 4.4.0** (`server/node_modules/exceljs/README.md`, `server/node_modules/exceljs/lib/doc/`):
- **No chart-creation API exists.** There is no `lib/doc/chart*` module, and the only chart-related README hit across the entire file is a changelog line from version 0.8.2 ("Don't break when loading an Excel file containing a chartsheet") — a **read-tolerance** fix (the library won't crash opening a file that already has a chart), not a chart-writing capability. ExcelJS cannot generate native Excel chart objects at this version.
- **Does** support raster image embedding: `workbook.addImage({ filename | buffer, extension })` returns an `imageId`, then `worksheet.addImage(imageId, 'B2:D6')` (or an explicit `{tl, br}`/`{tl, ext}` anchor) embeds it over a cell range, with a documented `addBackgroundImage` variant too. This requires the caller to supply already-rendered PNG/JPEG bytes.
- Already used by `xlsxBuilder.ts` for the existing metadata section, numeric/currency/date `numFmt` cell formatting, and frozen header row — all reused unchanged by this proposal.

**Conclusion:** the toolchain can draw vector shapes and embed raster images in PDF, and can embed raster images (but not native charts) in XLSX — but **nothing in the current dependency tree can rasterize a chart to PNG bytes**. This directly shapes the XLSX decision in §10.

## 8. Proposed server-owned chart contract

An optional, server-owned `chart` field is added to `ReportDefinition<TRow, TFilters>` in `types.ts`:

```ts
export type ExportChartType = 'line' | 'bar' | 'area' | 'pie' | 'donut';

export interface ExportChartSeriesDefinition {
  /** Must be a key present in ReportDefinition.columns — never a free string. */
  valueKey: string;
  /** Localization key resolved the SAME way column headers are (Record<SupportedExportLocale,string>) — never raw text. */
  labelKey: string;
}

export interface ExportChartDefinition {
  type: ExportChartType;
  /** Localized like ReportDefinition.title — Record<SupportedExportLocale,string>, resolved server-side. */
  titleKey: string;
  /** Must be a key present in ReportDefinition.columns and typed 'date' | 'text' — the x-axis / category axis. */
  categoryKey: string;
  series: ExportChartSeriesDefinition[];
}

export interface ReportDefinition<TRow, TFilters> {
  // ...existing fields (§6)...
  /** Optional. Absent = no chart is generated for this report (current behavior, unchanged). */
  chart?: ExportChartDefinition;
}
```

This closely tracks the illustrative contract given in the task brief, with one deliberate change validated against the existing architecture: `titleKey` and `series[].labelKey` are **not** free localization-file keys resolved through i18next (the server has no i18next runtime — confirmed by `exportStrings.ts`'s own doc comment) — they are resolved through the **same `Record<SupportedExportLocale, string>` map pattern already used for `ReportDefinition.title` and `ReportColumnDefinition.header`**. This means a chart's title and series labels are literally reference the definition's own already-localized, already-server-owned strings, not a new localization surface.

### Ownership
The chart definition lives entirely inside the server-owned `ReportDefinition` object in `registry.ts`, next to `columns`/`allowedRoles`/`maxSyncRows`. It is never constructed from request input. For the pilot, `revenueByPeriodDefinition.chart` would be a single `bar` or `line` series over `categoryKey: 'period'`, `series: [{ valueKey: 'revenue', labelKey: <localized "Revenue"> }]` — reusing the `period`/`revenue` column keys that already exist in `revenueByPeriodDefinition.columns`.

### Validation
`categoryKey` and every `series[].valueKey` are validated (ideally at module-load time, via a small assertion helper called once when `REPORT_DEFINITIONS_MAP` is built, mirroring the existing `allowedRoles`-mirrors-`authorize()` test-time assertion pattern in §12 of the test file) to be keys that exist in `definition.columns`. This makes an invalid chart definition a **build-time/test-time failure**, never a runtime client-triggerable state — there is no code path by which a client request can select an arbitrary `valueKey`/`categoryKey`, because the chart definition is not parsed from the request at all.

### Localization
`titleKey` resolves via the definition's own locale map (same pattern as `title`); series labels resolve the same way. No hardcoded Turkish (or any single language) anywhere in the chart-rendering code — every string source is `Record<SupportedExportLocale, string>`, matching `EXPORT_METADATA_STRINGS`'s existing TR/EN/FR/DE coverage.

### Data derivation
The chart never gets its own query. It is derived **in the route handler**, after `definition.loadRows(...)` returns the same `rows` array already used for the table, via `definition.toColumnValues(row)` — the identical mapping function the table renderer uses. This guarantees (by construction, not by convention) that the chart and the table can never disagree, and that the chart is subject to the exact same clinic-scope, role, filter, and row-limit gates as the table, because it consumes the table's own already-authorized output.

### Deterministic ordering
The chart's category axis order is simply the `rows` array order — the same `ORDER BY period_start` order already returned by `getRevenueByPeriodRows`. No independent client- or chart-side sort is ever introduced.

### Number/currency/date formatting
Reuses `formatCell`'s existing per-`ReportColumnType` `Intl.NumberFormat`/`Intl.DateTimeFormat` logic (`pdfBuilder.ts`) for axis/legend value labels — a chart never introduces a second number/date-formatting implementation.

### Missing-value behavior
`revenue`/`count` are already `COALESCE`d to `0` in `getRevenueByPeriodRows`'s SQL (§6), so there is no null-value case for the pilot's numeric series. As a general contract for future report definitions: a `null`/`undefined` value at a given category renders as `0` for the chart series (explicit, documented, never silently dropped — dropping a point would misalign the category axis across multiple series).

### Unsupported-chart-type / error / fallback behavior
`ExportChartType` is a closed TypeScript union; an "unknown type" is not a reachable runtime state for a value that only ever originates from `registry.ts`. As defense in depth, the chart-rendering step is wrapped so that **any renderer failure (including a hypothetical future unrecognized type) falls back to omitting the chart and still returning the table-only export** — a chart-rendering defect must never turn into a `GENERATION_FAILED` 500 for a request that would otherwise have succeeded before this feature existed. This preserves the existing route's error contract (§6/§9 of the ClickUp task's stop-condition philosophy: don't let an additive feature regress a previously-working path).

## 9. PDF options and decision

| Option | Security | Deterministic | Native deps | Container compat | Memory | CPU | Font/TR-FR-DE | Testability | Maintainability | Worker isolation | Failure modes |
|---|---|---|---|---|---|---|---|---|---|---|---|

| 4. Headless Chromium | Lowest — full browser engine (JS/CSS/font/image parsers) as attack surface for rendering a bar/line chart | Can be made deterministic but requires careful, ongoing font/flag pinning across host/container updates | Large native binary (~300MB+), sandbox flags, matching glibc | Requires explicit container image changes, sandboxing flags, headless-safe launch args | High (full browser process) per export | High (browser boot + page render) per export | Would need explicit font installation/embedding to guarantee TR/FR/DE glyphs render identically across environments | Achievable but heavyweight (screenshot-diff or DOM-serialization based) | Highest ongoing burden (browser upgrades, CVEs, flag drift) | Would need worker isolation almost immediately, given process weight | Browser crash/OOM/timeout under concurrent exports; largest blast radius of any option |

**Decision: Option 1 — constrained vector drawing directly through pdfkit's own path/shape primitives.**

- **Selected option:** Build a small, additive `chartRenderer.ts` (or equivalent) that takes the same `rows`/`toColumnValues` already passed to `buildReportExportPdfBuffer` plus the report's `ExportChartDefinition`, computes plain numeric geometry (bar x/y/width/height, line point coordinates, pie/donut arc angles) from validated, already-typed column values, and issues `doc.rect(...)`, `doc.moveTo/lineTo(...)`, and `doc.path('M...L...Z')` calls (pdfkit's own SVG-path-data mini-language, fed only by numbers this module computed itself — never externally supplied markup) directly into the existing `PDFDocument` instance already open in `buildReportExportPdfBuffer`. Text (title/axis/legend labels) uses the same registered `NotoSans`/`NotoSans-Bold` fonts and `Intl.*` formatting already in `pdfBuilder.ts`.
- **Rejected alternatives:** PNG-from-SVG (Option 2) and a third-party chart library (Option 3) both require a new dependency this task is explicitly barred from installing, and neither closes any capability gap pdfkit's native drawing primitives don't already cover for line/bar/area/pie/donut charts of aggregate report data. Headless Chromium (Option 4) is rejected per the task brief's explicit instruction not to recommend it "merely because it is convenient" — it is categorically disproportionate (native binary, large attack surface, heavy per-export CPU/memory, new container/worker-isolation requirements) for rendering a handful of geometric shapes that pdfkit already draws natively.
- **Risks:** (1) hand-rolled geometry math for pie/donut arc paths must be gotten right (angle-to-path-data conversion) — mitigated by unit-testing the pure geometry-computation function independently of pdfkit, with exact numeric assertions (no pixel snapshots). (2) A wide category count (e.g., a `revenue-by-period` export grouped by `day` over a long date range, up to `maxSyncRows` = 2000 categories) could render an illegible chart — this is a **rendering-quality** concern, not a security one; see §14 for the recommended mitigation (an explicit, separate, small chart-category cap).

- **Rejected alternatives:** Native chart objects (Option 1) are **not implementable** with the currently pinned `exceljs` version — this is a verified library-capability gap, not a design preference (§7). ## 11. Runtime/process-placement assessment

The chart step is added **inside the same synchronous request/response cycle already used for the table** — no new runtime placement decision is introduced.

- **CPU cost:** The PDF chart renderer (§9) performs `O(n)` vector-drawing calls over the same `rows` array already iterated once to build the table (`n <= maxSyncRows = 2000` for the pilot). This is asymptotically identical in shape to the existing per-row table-cell layout loop in `buildReportExportPdfBuffer` — no new order-of-magnitude cost.
- **Memory cost:** No new buffering of intermediate raster data (Option 1 draws vectors directly into the already-open `PDFDocument`, per §9's decision). XLSX carries zero additional memory cost (§10's decision adds nothing to the workbook).
- **Timeout risk:** Unchanged from today — bounded by the same `maxSyncRows` cap that already bounds the table-rendering time.
- **Concurrent export risk:** Unchanged — the export route today already runs fully synchronously per request with no queue; this feature adds work proportional to, and smaller than, the existing table-rendering work per request, so it does not change the concurrency risk profile the existing pilot already accepted.
- **API event-loop impact:** `pdfkit`'s and `exceljs`'s buffer-building calls are synchronous CPU work inside the request handler (as they already are today for the table) — this was already an accepted characteristic of the existing US-07.3-P1 foundation, not a new one introduced by charts.
- **Is a worker needed now:** No. The evidence above shows the chart step is strictly smaller than, and runs alongside, work the API process already performs synchronously today for the same request. Introducing a worker/queue for this would be new infrastructure unsupported by any measured or projected resource evidence, and is explicitly out of scope per the task brief ("Do not introduce queues, object storage, background jobs, Kafka, or new infrastructure unless evidence proves they are required for this narrowly scoped pilot").
- **Follow-up threshold:** If a future report definition needs a chart with materially more series/points than `revenue-by-period` (e.g., a multi-series, per-practitioner breakdown at the full `maxSyncRows` cap), worker isolation should be revisited then, based on measured render time under that report's own row/series bounds — not preemptively for this pilot.

## 12. Security and tenant-scope analysis

Every security property already proven for the table export is inherited unchanged by the chart, because the chart consumes the table's own already-authorized data (§8, "Data derivation"):

- **Organization scope:** unaffected — the chart never queries; it reads from `rows`, which `validateAndGetClinicIdScope` + `definition.loadRows` already produced under organization scope before the chart step runs.
- **Clinic scope:** same — `scope` (a `ClinicIdScopeWhere`) is resolved once, before `loadRows`, and both the table and the chart consume the same resulting `rows`.
- **User authorization:** unaffected — `isRoleAllowedForReport(user, definition.allowedRoles)` gates the entire request before any rows are loaded; a chart is never rendered for a request that would have been rejected today.
- **Report-level permissions:** the `chart` field lives on the same `ReportDefinition` object as `allowedRoles`/`pii`/`maxSyncRows` — there is no separate permission surface to keep in sync.
- **Server-owned query behavior:** unaffected — no new query is introduced; `getRevenueByPeriodRows` (§6) remains the single source of truth for both the JSON report, the table export, and now the chart.
- **Formula-injection protections:** N/A to the chart itself (chart values are drawn as numeric vector geometry / raster pixels, never written back into a spreadsheet cell as text), but the table's existing `neutralizeFormulaInjection` protection is completely unaffected — the XLSX decision (§10) adds no new text cells.
- **Row limits:** unaffected — the chart is built from the same `rows` array already capped by `exceedsSyncRowLimit`/`maxSyncRows`; it cannot itself cause a request to load more rows.
- **PII/audit behavior:** unaffected — `shouldAuditReportExport`/`recordReportExportAudit` continue to be driven purely by `definition.pii`; adding `chart` to a definition does not change its PII classification, and the chart draws no fields beyond what `toColumnValues` already exposes to the table.
- **Backend authorization independent of frontend visibility:** the `enablePdf`/chart-toggle UI in `ReportExportControls.tsx` is cosmetic only — exactly like today's `enablePdf` prop, which does not itself grant PDF export (the server-side `isRoleAllowedForReport` check does). A client could theoretically call the export endpoint with any UI state; the response shape is entirely determined server-side by `definition.chart`'s presence, never by a request parameter.
- **Client cannot select an arbitrary data source or value path:** by construction (§8), the chart contract's `categoryKey`/`series[].valueKey` are validated against `definition.columns` at definition-authoring time (module load), and the contract itself is never parsed from `req.query` or any other client input — there is no `chart`-shaped request parameter at all. This directly satisfies the task's requirement that "the client must not be able to select arbitrary data sources or chart value paths outside a server-defined allowlist."

## 14. Resource and scalability assessment

- **Bounding factor:** `maxSyncRows = 2000` for `revenue-by-period`, unchanged.
- **Chart-specific risk not present in the table today:** a `revenue-by-period` export grouped by `day` over a wide date range could return up to 2000 distinct periods (rows), each becoming one chart category. A 2000-bar or 2000-point chart is legible in a table but not in a chart image — this is a **rendering-quality** issue, not a resource/security one.
- **Recommended mitigation (documented here as an open design point for the implementation slice, not implemented in this document):** either (a) a separate, smaller, explicit chart-category cap (e.g., render only the chart when `rows.length` is within a documented, much smaller bound, and otherwise omit the chart with the same "fall back to table-only" behavior already specified in §8's error/fallback contract — never a 500), or (b) leave category density entirely to the report definition's own choice of `groupBy` default and document the limitation. Either choice is implementation-detail scope, not an architectural blocker — both are compatible with every decision recorded above.
- **CPU/memory:** see §11 — strictly bounded by, and smaller in order of magnitude than, the existing table-rendering work for the same `maxSyncRows`-capped row count.
- **No queue/object storage/background job is justified** by any measured or projected cost above; §11's conclusion stands.

## 15. Testing strategy

Extends the existing `server/src/tests/reportExportFoundation.test.ts` convention (§6: no live database, `tsx`-script harness, real `pdfkit`/`exceljs` buffer generation, `exceljs` re-parse for real cell/image assertions, `node:assert/strict`) — either as new `section()` blocks in that file or a sibling `reportExportChart.test.ts` following the identical pattern.

| Test case | Test type | Requires |
|---|---|---|
| Chart contract validation (`categoryKey`/`valueKey` must reference an existing column) | Unit | None (pure function / module-load assertion) |
| Unsupported chart type is unreachable / falls back safely | Unit | None (TypeScript exhaustiveness + a defensive runtime branch test) |
| Chart data comes from the identical `rows`/`toColumnValues` as the table (same filter inputs) | Unit / source-shape assertion (same regex-over-source technique already used for role-list mirroring in the existing test file) | None |
| Deterministic chart series ordering (matches `rows` array order, no independent re-sort) | Unit | None |
| Empty data (`rows.length === 0`) | Functional | Real `pdfkit` buffer generation (mirrors the existing "never throws for an empty row set" test) |
| Single data point | Functional | Real `pdfkit` buffer generation |
| Multiple series | Functional | Real `pdfkit` buffer generation |
| Negative or zero values where valid (e.g., a future report with negative deltas) | Unit (geometry math) + functional (renders without throwing) | None / real buffer generation |
| PDF chart asset presence | Functional — parse the generated PDF buffer's content stream and assert the expected vector-drawing operators (path/rect fill+stroke ops) are present, the same "well-formed PDF buffer" style already used in the existing test file (never a pixel-diff/visual snapshot) | Real PDF buffer generation |
| XLSX native chart or embedded image presence | N/A for the pilot decision (§10) — instead, assert the workbook contains **no** chart/image part and the table is byte-identical in shape to today's output, proving the fallback is truly a no-op | Real ExcelJS buffer generation + re-parse (`exceljs` ZIP/XML reading, already the existing test file's technique) |
| Corrupted asset failure handling | Unit — force the chart-rendering function to throw and assert the route still returns a valid table-only export (never `GENERATION_FAILED` for a pre-existing-working request) | Route-level test with a stubbed renderer, or a direct unit test of the try/catch fallback boundary described in §8 |
| TR/EN/FR/DE labels and characters | Functional — mirrors the existing "Turkish diacritics... survive byte-for-byte" test, extended to chart title/axis/legend text | Real buffer generation (PDF text extraction or XLSX text re-parse, matching existing technique) |
| Tenant-scope regression | Source-shape assertion — the chart step must not introduce a new code path that loads rows before `validateAndGetClinicIdScope`, mirroring the existing "denied clinic scope returns before any row loading" test | None (regex-over-source, existing technique) |
| Formula-injection regression | Unit — confirm the XLSX fallback decision (§10) introduces no new text cells, so `neutralizeFormulaInjection` coverage is unchanged | None |
| Row-limit regression | Unit — confirm `exceedsSyncRowLimit` is still checked before any chart-rendering call | Source-shape assertion, matching the existing "route rejects... before building any file" test |
| File-open/round-trip validation | Functional — re-open the generated XLSX with `exceljs` (proves the file is still valid after the change) and validate the PDF buffer's basic structural well-formedness (as the existing test file already does for the table-only PDF) | Real buffer generation |
| No fragile pixel-perfect snapshots | Design constraint applied throughout — every chart assertion above is either a numeric/geometric assertion, a structural (operator/part-presence) assertion, or a re-parsed-cell-value assertion, never an image-diff | N/A |

No disposable PostgreSQL instance is required for any of the above — consistent with the existing test file's "no live database" convention, since every chart input (`rows`) is either a hand-built fixture (unit tests) or produced by directly calling the already-tested `loadRows`/`getRevenueByPeriodRows` path only where the existing test file already does so.

## 21. Open risks and unknowns

1. **Chart-category density at high row counts** (§14) — needs an explicit product/design decision (cap vs. document-only) before implementation slice 3/4; not a blocker to this architecture's decisions, but should be resolved before the PDF pilot ships.
2. **XLSX chart parity gap** — until a PNG-rasterization dependency is separately evaluated and approved (§10), Excel users will not get an embedded chart image; only PDF will. This is a product-facing limitation to communicate, not a technical risk.
3. **Pie/donut arc-path geometry correctness** (§9) — the highest-complexity piece of new math in the whole proposal; must be unit-tested numerically (angle-to-path-data conversion) before relying on it, per §15.
4. **Future non-aggregate report definitions** — if a later report definition with `pii: true` ever adds a chart, the chart-data derivation module (§16 slice 2) must be verified to expose no more per-row detail via chart geometry (e.g., tooltips/labels) than `toColumnValues` already exposes to the table; this document's chart contract does not by itself prevent a future report definition from being poorly scoped, only the `revenue-by-period` pilot is evaluated here.
