# KVKK Remaining Application Code Gap Audit — 2026-07-24

Documentation-only, read-only, evidence-driven audit. No application code, test, Prisma schema/migration, feature flag, or environment/config file was read for the purpose of being changed, and none was changed. This document is the sole deliverable of this task.

## 1. Executive conclusion

**One concrete application-code defect was found that should be fixed before onboarding the first real clinic/patient**, and it is unrelated to any previously-closed KVKK control: the Excel patient bulk-import endpoint (`server/src/routes/patientsImport.ts`) resolves a `?clinicId=` query-string fallback into the target clinic for newly-created patient rows **without validating it against the caller's accessible clinics or organization**, allowing an authenticated RECEPTIONIST/CLINIC_MANAGER/ORG_ADMIN/OWNER to write real patient PII into an arbitrary clinic — including one belonging to a different organization — via the ordinary "import patients from Excel" feature. This is a demonstrated authorization-bypass write path, not defense-in-depth hardening, and it sits directly beside the codebase's own correct pattern for the same problem (`server/src/routes/usersImport.ts`). See Finding H1.

With that one exception, this audit found the previously-completed KVKK controls (KVKK-HIGH-006 tenant-scope remediation, KVKK-HIGH-008/R-061 legacy-consent kill switch, KVKK-HIGH-004 secure bulk export, KVKK-CRIT-003 security incident response) to be genuinely and consistently implemented in current code — not merely claimed in tracker documents — across the eight categories audited. A small number of additional lower-severity code findings were identified (four `CODE_REMEDIATION_RECOMMENDED`, none rising to a second blocker) and are listed in Section 5/6. Attachment/imaging encryption remains an `INFRASTRUCTURE_EVIDENCE_REQUIRED` item per the program's own pre-existing conditional rule (KVKK-HIGH-001), not a fresh code gap invented by this audit. Two documentation staleness issues were found and are separated from code findings per instructions.

**Direct answer to the mandated question ("does any KVKK-related application code need to be implemented before onboarding the first real clinic/patient?"): YES — one bounded fix (H1), scoped in Section 10.** Everything else found is either already closed, already documented as a deliberate deferral, a deployment/production-verification-only item, an infrastructure-evidence dependency, or optional hardening.

### A — Security incident response
All routes in `platformSecurityIncidents.ts` are gated by `authenticatePlatformAdmin` + `csrfProtection('platform')` (line 46); `PlatformAdmin` has no `role` field, so incident visibility is platform-admin-only by construction — never reachable from any clinic-user route. All three mandatory detection rules (auth brute-force, cross-tenant denial, export anomalies) have live call sites, not just definitions, in `auth.ts`, `platformAdmin.ts`, `clinicScope.ts`, `clinicAccess.ts`, and `clinicBulkExport.ts`/`clinicBulkExportPackage.ts`. Lifecycle transitions are enforced server-side via an `ALLOWED_TRANSITIONS` graph and compare-and-set `updateMany`. The frontend page (`src/pages/platform/PlatformSecurityIncidents.tsx`, 589 lines) is lazy-loaded and mounted inside the `<PlatformRoute>`-gated `/platform` layout in `src/App.tsx`. **No CODE_BLOCKER_BEFORE_ONBOARDING or CODE_REMEDIATION_RECOMMENDED finding in this category.** The mutation-endpoint rate limiter degrading to per-instance memory when Redis is unavailable is noted as `OPTIONAL_FUTURE_HARDENING` (it is explicitly a secondary control by its own code comment). `docs/compliance/55-kvkk-security-incident-response-foundation.md`'s header ("In progress... not merged, not deployed") is stale against current code — see Section 7.

### B — Secure clinic bulk export (KVKK-HIGH-004)
The legacy `gdprExport.ts` GET route unconditionally returns `410` and cannot be reactivated by any parameter. `clinicBulkExportConfig.ts` fails closed on anything but the literal string `'true'`, re-checked at four independent points during generation, not just at request time. Authorization is `OWNER`/`ORG_ADMIN`-only via `authorize()`, clinic scope via `validateAndGetScope` (never raw `clinicId`). Step-up auth performs a real `bcrypt.compare` against the live password hash inside a Postgres-advisory-lock-serialized, DB-authoritative lockout counter (`clinicBulkExportPasswordAttempts.ts`). The worker is registered in `startBackgroundJobs.ts` and runs on a 1-minute cron with cross-replica-safe claiming. Rate limiting/concurrency (cooldown, daily cap, active-job check) run inside one Postgres transaction backed by a DB partial unique index. Download tokens are SHA-256-hashed at rest, single-use via a guarded `updateMany`, and TTL-enforced. Archive cleanup calls a real `deleteFile()` (S3 `DeleteObjectCommand` or `fs.unlink`), not just a DB-row null-out, and self-heals on retry. Every entity query during generation is scoped by the job's own persisted `clinicId` (resolved once at reservation time), and download-claim independently re-checks `clinicId`/`organizationId`. **No CODE_BLOCKER_BEFORE_ONBOARDING or CODE_REMEDIATION_RECOMMENDED finding in this category.** `docs/compliance/KVKK_COMPLIANCE_AUDIT_AND_REMEDIATION.md` still describes this control as "Merged — awaiting deployment and production verification," which is stale — see Section 7.

This is **not a newly-discovered gap**: the program's own `KVKK_COMPLIANCE_AUDIT_AND_REMEDIATION.md` (KVKK-HIGH-001, line 96) already states the exact conditional rule this audit was told to apply — the item "stays Phase 1 only if infra encryption checklist... passes; otherwise becomes a Phase 0 blocker." That infra checklist (VPS disk encryption, Postgres storage-level encryption, backup-script encryption, Hostinger snapshot encryption, key rotation policy) is independently corroborated as outstanding/unverified — not confirmed passing, not confirmed failing — by `docs/architecture/object-storage-backup-migration-design.md` §12 and `docs/operations/pilot/PILOT_BACKUP_RESTORE_AND_FILE_COVERAGE_AUDIT.md`. Per the program's own pre-existing rule, this stays classified `INFRASTRUCTURE_EVIDENCE_REQUIRED` rather than being converted into a new code task by this audit; if the infra checklist later comes back negative, the program's own document already specifies it flips to a Phase-0 code blocker at that point, not before. No key-rotation mechanism exists for attachments (none is needed today — nothing is encrypted); the WhatsApp-provider-secret single-key `encryption.ts` utility has no rotation path either, classified `OPTIONAL_FUTURE_HARDENING`. Download authorization was independently verified correct on every attachment/imaging/lab-attachment route: each does a scoped `findFirst`/relation-scoped lookup (via `validateAndGetClinicIdScope` or `getAccessibleClinicIds`) *before* calling `openFileStream`, never after. Path-traversal protection is structural — `buildStorageKey()` derives the storage key entirely server-side, and `isSafeStorageKey()` independently rejects absolute paths, UNC prefixes, and `..` segments — with one noted (non-exploitable today) defense-in-depth gap: `openFileStream()`/`deleteFile()` themselves don't call `isSafeStorageKey()`, relying on every current call site only ever passing back a DB-stored, previously-validated key. Classified `OPTIONAL_FUTURE_HARDENING`.

### E — Retention, deletion, anonymization
`dataRetentionCleanupJob.ts` is registered in both runtime topologies (`startBackgroundJobs.ts` → `index.ts` for the API process gated by `RUN_BACKGROUND_JOBS`, and unconditionally in `worker.ts`), never touches `Patient`/`Appointment`/`Treatment`/`Payment`/`Attachment`/`AuditLog`/`ActivityLog`, uses per-category try/catch so one failure doesn't abort the run, and reads retention windows from configurable, safely-defaulted settings rather than hardcoding them. Its execution additionally requires `PlatformSetting` key `privacy.dataRetention.runtimeEnabled==='true'` — a deliberate, fail-closed, admin-auditable pattern matching the KVKK-HIGH-008 kill-switch convention already accepted elsewhere in this program — but this audit found **no documented evidence of that setting's current production value** anywhere in `PRODUCTION_TOPOLOGY.md`/`ENVIRONMENT_MATRIX.md`/existing evidence docs; if it has never been enabled, several PII-bearing tables (`WhatsAppConversationMessage`, `OperationalEvent`, `MessagingInboundEvent`) are growing unbounded in production despite correctly-written cleanup code. Export-archive cleanup jobs (`patientPrivacyExportCleanupJob.ts`, `clinicBulkExportCleanupJob.ts`) are registered, delete physical files before/alongside DB rows, and are self-healing on partial failure. Attachment/imaging physical-file lifecycle is consistent — the one live delete path (`attachments.ts`) always deletes the physical file after an atomic, legal-hold-respecting DB delete; imaging has no delete path at all (archive-only), so no imaging-orphan risk exists. `patientAnonymization.ts` clears every direct-identifier field that exists on the `Patient` model (there is no Turkish national-ID field on this schema at all, so that specific historical concern is structurally inapplicable, not merely redacted). `AuditLog`/`ActivityLog` retention is a documented, intentional non-deletion policy pending legal sign-off — a legal decision, not a code inconsistency. Two gaps were found: the `Notification` table (patient name/phone in `title`/`subtitle`, created via `upsertNotification()` in `notifications.ts`) has no cleanup job and is not touched by anonymization, so a patient's pre-anonymization name can persist indefinitely in a historical notification row; and `LabOrderAttachment` has no `legalHold` field at all (unlike its sibling `PatientAttachment`/`ImagingStudy` models), so a lab-order file cannot be protected from deletion the way the program's own established pattern protects equivalent attachment types.

### F — Authentication and privacy administration
`PlatformAdmin` JWTs are stateless and cannot be invalidated after a password reset (`platformAuth.ts:18-63`, signature+`jti`-presence check only; no `passwordChangedAt` column exists on `PlatformAdmin`, unlike the clinic-side `User` model, which correctly implements this exact check at `auth.ts:142-150`). This is not a new or undocumented risk: it is precisely the limitation the program itself already surfaced and closed as part of R-061 on 2026-07-24 (`sessionsInvalidated: 0`, quoted verbatim in `RISK_REGISTER.md` line 3 as "a documented limitation of PlatformAdmin's stateless-JWT sessions, not a new gap"), and the recovery runbook already names the correct fix (`passwordChangedAt` column mirroring `User`) as tracked future work. Password recovery's DB write payload contains only `{ passwordHash }` — no TOTP fields are touched, so MFA state is correctly preserved by construction, not merely by claim. Platform-admin sessions are cookie-only (bearer fallback requires an explicit, logged opt-in flag), `httpOnly`, CSRF-protected via an HMAC-signed token bound to the session's own `jti` plus an origin allowlist. Secret rotation is a standard single-env-secret pattern with no `kid`/multi-secret support — rotating today forces a mass re-login rather than a graceful rollover; this is a normal operational tradeoff at this program stage, not a documented gap or a defect, classified `OPTIONAL_FUTURE_HARDENING`. Audit actor attribution correctly records the authenticated caller's own re-derived ID from the verified JWT, with the one legitimate `null`-actor exception (the password-recovery CLI itself, where no authenticated actor exists by construction) honestly disclosed rather than faked.

### G — Logging and secret/PII exposure
The core `pino`/`pino-http` logger (`server/src/utils/logger.ts`) redacts `Authorization`, `cookie`, and `set-cookie` headers, strips token/secret/key query params via `maskUrl()`, and by design and comment never logs the request/response body. No wholesale `req.body`/raw-payload logging was found anywhere (grep-confirmed). No password/token/secret/credential value logging was found in any HTTP-reachable path — the two near-misses found are both non-HTTP CLI scripts that log only non-secret metadata. The Instagram provider's error-logging path deliberately redacts tokens (8-character prefix only, `redactMetaBody()` strips `access_token` from bodies and URLs before logging). Communication-consent audit logging is PII-free by construction (verified: no `patientId`/phone/email/message-text field is ever included in its persisted payload). One concrete, previously-undocumented finding: `server/src/routes/whatsapp.ts:3665-3669` and `:3735-3740` log the raw, unredacted `incomingMessage.phone` via `console.info` in the Evolution WhatsApp webhook handler, even though a `redactPhone()` helper is defined in the same file and is correctly applied at 25+ other log sites in that same file — including the structurally-sibling branch of the exact same log message at line 3818, just ~80 lines later. This is a clear, isolated, cheaply-fixable oversight, not a systemic redaction-policy gap.

### H — Multi-tenant privacy boundaries
**H1 (the one CODE_BLOCKER_BEFORE_ONBOARDING of this audit).** `server/src/routes/patientsImport.ts`, function `validatePatientRows()` (lines 107-219), called from `POST /api/patients/import-confirm` (lines 269-380) and `POST /api/patients/import-preview` (lines 224-264), both authorized for `IMPORT_ROLES = ['OWNER','ORG_ADMIN','CLINIC_MANAGER','RECEPTIONIST']` (line 57). Independently re-read and confirmed by the lead agent directly (not merely accepted from sub-agent research): at lines 179-193, per-row `clinicId` (an optional Excel column) is validated against `accessibleIds` (line 184, correct), but the fallback branch — `else if (selectedClinicId && selectedClinicId !== 'all') { resolvedClinicId = selectedClinicId; }` (lines 189-190) — performs **no check of any kind**, neither against `accessibleIds` nor against `organizationId`. `selectedClinicId` is `req.query.clinicId` (lines 233, 279), a raw, caller-controlled query-string value. This resolved value flows to `row.data.clinicId` (line 211), then in `import-confirm` to `const clinicId = row.data.clinicId as string` (line 303), used unguarded in `prisma.clinic.findUnique({ where: { id: clinicId }, select: { maxPatients: true } })` (lines 304-307, no `organizationId` filter) and then `prisma.patient.create({ data: { organizationId: orgId, clinicId, firstName, lastName, phone, email, ... } })` (lines 318-332) — a real patient record is created with the caller's true `organizationId` but an attacker-chosen `clinicId`. `Patient.clinicId` and `Patient.organizationId` are independent foreign keys in `schema.prisma` (lines 217-218, 237-238) with no compound constraint tying them together, so nothing in the database schema itself prevents this mismatch. Independently confirmed the gap is exercised, not merely untested: `server/src/tests/excelImport.test.ts:628` explicitly asserts the query-fallback path as *valid* with no accessible-clinics check, mirroring the real logic. Independently confirmed the correct pattern already exists one file away: `server/src/routes/usersImport.ts:178-188` derives the identical row-or-query-fallback `clinicId`, but then *unconditionally* validates every resulting ID against `accessibleIds` regardless of which path produced it (verified directly, lines 178-186) — `patientsImport.ts` simply omits that final check for the fallback branch. **Reachable call path:** an authenticated RECEPTIONIST (or higher role) restricted to Clinic A calls `POST /api/patients/import-confirm?clinicId=<any-clinic-uuid-in-the-database>` with a normal `.xlsx` file whose rows leave the optional `clinicId` column blank; the resulting patients are created under the attacker-supplied clinic regardless of the caller's actual clinic assignment or organization. **Realistic triggering condition:** any multi-tenant production deployment (this platform already hosts multiple organizations, per `RISK_REGISTER.md`'s own KVKK-HIGH-006 production evidence) — no special access or timing is required, only knowledge or guessing of another clinic's UUID. **Proposed regression test:** authenticate as a RECEPTIONITST with `allowedClinicIds=['A']`, `canAccessAllClinics:false`; call `import-confirm?clinicId=B` where B is outside `allowedClinicIds` (or belongs to a different organization); assert `403`/`400` and zero patient rows created — this currently succeeds and creates the row. **Smallest safe remediation boundary:** validate `selectedClinicId` against `accessibleIds` (and against `organizationId`, via the existing `validateAndGetScope`/`buildClinicScopeWhere` helper already used elsewhere in this codebase) before it is used as the fallback at line 189-190, mirroring `usersImport.ts:185-188`; additionally add an `organizationId` filter to the `clinic.findUnique` maxPatients lookup at line 304-307 as defense-in-depth. No schema/migration change is needed.

**H2.** `organizationWhatsApp.ts` (`GET`/`PUT .../whatsapp`) and all three `organizationInstagram.ts` connection routes authorize `CLINIC_MANAGER` at the role level and check the target clinic belongs to the caller's *organization*, but never check it against the caller's own `allowedClinicIds` — despite the helper functions' own doc comments explicitly stating "CLINIC_MANAGER: only their own branch." The correct pattern (a local `getAllowedClinicIds()` intersection) already exists one file away in `whatsappInbox.ts`/`instagramInbox.ts`. This is same-organization-only (not cross-tenant across different customers), does not expose secrets (tokens are stripped before response), and does not expose patient data — a same-tenant, cross-branch least-privilege gap that is structurally inert for any organization with only one clinic. Classified `CODE_REMEDIATION_RECOMMENDED`, not a blocker for a first single-clinic customer, but should be fixed before a second branch/CLINIC_MANAGER-role combination goes live for any given organization.

**H3.** Six legacy bot-integration routes in `whatsapp.ts` (services/doctors/availability/appointment-lookup/appointment-requests/cancel-request under `/api/public/whatsapp`) use `getDefaultClinic()` — literally the oldest clinic row in the entire database, globally, with no per-instance/connection resolution, unlike the main Evolution webhook handler which correctly resolves the target clinic per connection. This is trivially correct with exactly one clinic in the database and becomes a real cross-tenant risk only once a second clinic exists **and** this legacy surface is still wired to live external traffic — which this audit could not determine from static code alone. Classified `CODE_REMEDIATION_RECOMMENDED` for the code pattern itself, `INFRASTRUCTURE_EVIDENCE_REQUIRED` for whether this specific legacy surface is still live in production.

**Task: Fix unvalidated clinic-scope fallback in patient Excel bulk import.**

As defense-in-depth, add an `organizationId` filter to the `clinic.findUnique` call used for the `maxPatients` check in `import-confirm`, so a clinic ID that somehow reaches that point without passing the earlier check still cannot resolve to a foreign-org clinic.

- **Deployment impact:** standard backend-only deploy, no new environment variable, no feature flag, no worker/job-registration change, no frontend change required (the frontend already only offers the user's own accessible clinics in its clinic selector — this is a server-side validation gap, not a UI change).

## 12. Residual limitations and non-claims

- This audit does **not** claim legal KVKK compliance for the platform as a whole. It is a code-focused, application-layer technical review of eight specific categories; it does not cover contractual/DPA status, VERBİS registration, legal-basis documentation completeness, or any determination reserved for legal counsel.
- This audit does **not** claim the "KVKK baseline is stable" as an overall program declaration — that declaration has its own separate gating conditions (freeze-boundary condition 4, F0-011-P2 evidence chain) tracked elsewhere in the program and unaffected by this task.
- This audit is a point-in-time, read-only source-code review against one specific commit (`a290b6f45178539508be69e63717570d2a48ed4`). It does not constitute production verification of any control — where a control's *production* state (as opposed to its code) was relevant and unverified (E3, and the KVKK-HIGH-004 production-behavioral-smoke gap noted in Section 7), this was explicitly separated from the code finding rather than assumed.
- Findings D1-D3 (communication-consent evaluator bypasses on three outbound paths) are real code-level facts, independently re-confirmed by this audit, but they are already known, already documented in `docs/compliance/56-...md`, and currently inert because enforcement defaults off — this audit did not discover them as new risks, only re-verified that the documentation's characterization of them remains accurate.
- This audit is not exhaustive. It targeted the eight named categories and representative call sites within them; it did not attempt full route-by-route coverage of every endpoint in `server/src/routes` (over 60 files), nor did it review frontend code beyond the one platform-admin page cited in Category A, nor did it execute any test suite, run a static analyzer, or query a live database.
- No finding in this document reopens, modifies, or proposes modifying KVKK-HIGH-006 or KVKK-HIGH-008/R-061 controls; both were treated strictly as closed baseline throughout, per the task's explicit restriction.
