## 9. PostgreSQL provisioning options considered

| Option | Description | Assessment |
|---|---|---|
| **A — New disposable container per run, one database inside it** | `docker run --rm -d postgres:16-alpine` per run, container's own `POSTGRES_DB` set to the run's deterministic database name; migrations applied once via `prisma migrate deploy`; container torn down at run end. | **Selected (§10).** Matches all 3 historical precedents exactly. Total isolation (separate process, separate storage, separate connection namespace) — a killed test process cannot corrupt another run's data because there is no shared container. Highest resource cost (~1 Postgres process per run) but this repository's own test volume (22 files, not thousands) makes that cost negligible. |
| **B — New database on a long-lived shared disposable container** | One container stays running (locally or as a long-lived CI service), each run does `CREATE DATABASE <name>` against it. | Rejected as the **primary** model. Reduces container-start latency but reintroduces exactly the shared-connection-pool/`pg_stat_activity`/`max_connections` contention this design is trying to eliminate, and requires an explicit `CREATE DATABASE`/`DROP DATABASE` step with its own failure modes (a leaked database from a killed run now persists inside a *shared, otherwise-healthy* container, unlike Option A where the whole container's death takes the leak with it). Retained as an optional **local-developer convenience** variant only (§16), never as the CI default. |
| **C — Schema-per-run inside one shared database** | One container, one database, each run gets `?schema=run_<id>` and Prisma applies migrations into that schema. | **Evaluated, not selected** — see §D of the required-design-questions treatment in the companion JSON and the dedicated analysis in §13. Not proven safe against this repository's actual migration/test content. |
| **D — Ephemeral in-memory/sqlite substitute** | Swap Postgres for an in-memory or embedded database during tests. | Rejected outright, not seriously evaluated further: the application's `schema.prisma` `datasource db { provider = "postgresql" }` is Postgres-specific (grep-confirmed, §4), and several of the 22 dependent tests assert Postgres-specific behavior (e.g., `fileBackupDbIntegration.test.ts`'s race-condition test explicitly asserts the *absence* of a unique constraint at the DB layer, §4 Q4 — behavior that would not reproduce identically against a different engine). Substituting the engine would be an application-testability change this task is not authorized to make (and would contradict the task's own "no framework rewrite" boundary). |

## 10. Selected PostgreSQL design and rationale

**Selected: Option A — one disposable Postgres 16 container per run, one database inside it, ephemeral storage (no volume), deterministic naming (§13), non-default/dynamically-assigned host port (§12), migrated once via `npx prisma migrate deploy` before any dependent test runs.**

Rationale: this is the only option with 3 independent historical precedents in this exact repository, all of which succeeded (F0-011-P2: 3 databases across phases, KVKK-HIGH-006: 63/63 assertions, KVKK-HIGH-008-PMVR Phase B1: full migration-forward+rollback rehearsal). It requires zero new Prisma configuration (no `multiSchema` preview feature, no `schemas` datasource array — confirmed absent by this task's own grep, §4/§D). It provides the strongest possible collision guarantee: two runs cannot interfere with each other's `pg_stat_activity`, locks, or connection pool, because they are different processes entirely — the guarantee holds even if the naming algorithm in §13 were somehow defeated. Cleanup is total and unconditional: removing the container removes 100% of the run's database state, with no reliance on any test file's own `cleanupAllFixtures()` call ever actually executing (§4 Q9 already shows that in-test cleanup cannot survive a hard kill; this design does not depend on it for correctness, only for defense-in-depth against corruption of the *shared cleanup evidence trail*, not the shared server itself, because there is no shared server).

## 13. Port/database/schema/bucket isolation contract

**Naming algorithm (proposed, not yet implemented — a future implementation task's exact responsibility):**

```
runKey = first 12 hex characters of
  sha256(`${CI_RUN_ID || 'local'}:${CI_RUN_ATTEMPT || '0'}:${process.pid}:${branchOrWorktreeIdentifier}:${crypto.randomUUID()}`)

scopeTag  = 'ci' when running under a recognized CI environment variable, else 'local'
```

- **Container names:** `nmtest-pg-<scopeTag>-<runKey>`, `nmtest-minio-<scopeTag>-<runKey>` (e.g. `nmtest-pg-ci-a1b2c3d4e5f6`).
- **Database name:** `nmtest_<scopeTag>_<runKey>` (underscore-separated — Postgres unquoted identifiers fold to lowercase and reject hyphens without quoting; e.g. `nmtest_local_7f3a9c1e2b44`). Total length ≈ 22-24 characters, well under PostgreSQL's 63-byte (`NAMEDATALEN`) identifier limit, leaving headroom even if `scopeTag` grows.
- **Bucket name:** `nmtest-<scopeTag>-<runKey>` (hyphen-separated — S3/MinIO bucket-naming rules forbid underscores, require lowercase alphanumeric+hyphen, 3-63 characters; this algorithm's output satisfies that constraint by construction).
- **Branch/worktree identity is never embedded raw** — only folded into the sha256 input, so a branch name that happened to contain something sensitive (a ticket title, a person's name) never appears in a container name, database name, bucket name, or log line. This satisfies the task's explicit "without leaking sensitive content" requirement.
- **Cleanup prefix:** `nmtest` (containers), `nmtest_` (databases), `nmtest-` (buckets) — a sweeper matches exactly this prefix and must never touch anything else; this is a deliberately narrow, easily-greppable, collision-proof-with-real-data prefix (no production database or bucket in this program's history has ever used an `nmtest`-prefixed name, confirmed by this task's own review of `server/.env.example` and `fileBackupDestination.ts`, neither of which references any `nmtest`-prefixed identifier).
- **Uniqueness under parallel matrix jobs:** the CI-run-id + attempt + pid + random-UUID composite means two matrix legs of the *same* CI run still produce distinct `runKey` values (each leg has a distinct `process.pid` at minimum, reinforced by the random UUID); two entirely separate CI runs are further distinguished by `CI_RUN_ID`; two local runs on the same machine are distinguished by `process.pid` + a fresh `randomUUID()` each invocation.

**Port isolation (§B):**

- Host-port exposure is **not required for GitHub Actions** — a job's own steps can reach a `services:`-block container via `localhost:<mapped-port>` once a host port is mapped, but GH Actions supports requesting a **dynamic** host-port mapping (`ports: ["5432"]` without a fixed left-hand side) and reading the runner-assigned port via `${{ job.services.<name>.ports['5432'] }}` — this is the recommended CI approach, eliminating fixed-port collision risk entirely even though each matrix leg already runs on its own isolated runner VM (defense in depth, not strictly required by GH's own job-isolation model).
- For **local Windows execution** using raw `docker run` (not GH Actions' `services:` block), the recommended approach is `docker run -p 127.0.0.1::5432 …` (double-colon syntax: Docker itself assigns a free host port, avoiding any application-level "find a free port" race), then `docker port <container> 5432` to discover the assigned port before constructing `DATABASE_URL`. This avoids the classic discover-then-bind TOCTOU race entirely, because Docker's own bind already happened by the time the port is queried.
- The resolved port is communicated to test commands via `DATABASE_URL` (and `MINIO_ENDPOINT` for MinIO) constructed by the provisioning wrapper script and exported into the shell/step environment immediately before `npm run test:*`/`npx tsx` is invoked — never hardcoded into any test file (none of the 22+1 files construct their own connection string, §4 Q2, so this is a clean seam).

## 14. Setup/readiness/migration sequence

1. Generate `runKey`/`scopeTag` (§13).
2. Start the Postgres container (`docker run --rm -d --name nmtest-pg-<scopeTag>-<runKey> -e POSTGRES_DB=nmtest_<scopeTag>_<runKey> -e POSTGRES_USER=<test-only, generated> -e POSTGRES_PASSWORD=<test-only, generated, never logged> -p 127.0.0.1::5432 --label noramedi.disposable-runtime=true --label noramedi.run-scope=<scopeTag> --label noramedi.run-id=<runKey> --label noramedi.created-at=<ISO8601> postgres:16-alpine`), or declare the equivalent GH Actions `services:` block.
3. Poll `pg_isready` (or the GH Actions service `--health-cmd pg_isready` option) with a bounded timeout (recommend 60s) — timeout is a **fail**, not an extended retry (§J).
4. Discover the assigned port (`docker port` locally; `job.services.*.ports` in GH Actions); construct `DATABASE_URL`.
5. Run `npx prisma generate && npx prisma migrate deploy` against that `DATABASE_URL` — a non-zero exit or any reported pending migration is a **fail** (§J), never a silent continue.
6. (MinIO path only, for `fileBackupDbIntegration.test.ts`) Start the MinIO container analogously (`nmtest-minio-<scopeTag>-<runKey>`, freshly-generated credentials, `-p 127.0.0.1::9000`), poll `GET /minio/health/ready` with the same bounded-timeout-is-fail rule, export `MINIO_ENDPOINT`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`.
7. Invoke the target test command(s) with `DATABASE_URL`/`MINIO_*` set in the invoking process's environment only (never written to a committed `.env` file).
8. Run cleanup (§15) regardless of the test command's exit code.

No test file applies migrations itself (§4 Q3) — this sequence's step 5 is the only migration-application point, consistent with every historical precedent.

## 15. Cleanup and orphan-sweeper design

- **Normal success / test failure:** identical cleanup path in both cases — container removal (`docker rm -f nmtest-pg-<scopeTag>-<runKey>` and, if started, the MinIO container) — run from a `finally`/`trap EXIT`-equivalent block, never conditioned on the test command's own exit code. Because containers run with no volume mount, removal is total; no orphaned data directory can remain on disk.
- **Shell interruption (Ctrl+C/SIGINT/SIGTERM) on local Windows:** a PowerShell `try { … } finally { … }` block plus a `Register-EngineEvent PowerShell.Exiting` handler covers most interactive interruption paths, but this design explicitly records a **known gap**: PowerShell's signal-handling guarantees are weaker than POSIX `trap`, and a hard-killed PowerShell host (task-manager-killed, not Ctrl+C) will **not** run any `finally` block. This is exactly why the sweeper (below) is a required backstop, not an optional nicety.
- **CI cancellation:** GitHub Actions tears down the entire runner VM on job cancellation/completion — any `services:`-block container dies with it, no explicit cleanup step is even required for that path. This is a structural advantage of preferring native `services:` over a manually-invoked `docker run` step in CI specifically.
- **Stale-resource sweeper (local/worktree only — CI does not need one, per the point above):** a script that lists `docker ps -a --filter "label=noramedi.disposable-runtime=true"`, reads each container's `noramedi.created-at` label, and force-removes any older than a TTL (recommend 4 hours for local/worktree use — long enough to survive a normal working session, short enough to bound leakage). The sweeper must filter strictly on the `noramedi.disposable-runtime=true` label and must never remove an unlabeled container (this is the mechanism that keeps it from ever touching a developer's own unrelated Postgres/MinIO container).
- **Required labels:** `noramedi.disposable-runtime=true`, `noramedi.run-scope=<local|ci>`, `noramedi.run-id=<runKey>`, `noramedi.created-at=<ISO8601>` — set at `docker run --label` time, not inferred after the fact.
- **Cleanup command exit semantics:** cleanup failure (e.g., `docker rm` fails because the container already vanished) **warns**, loudly, and does not flip an already-green test result to failure — the sweeper is the actual backstop for resource leakage, not the per-run script's own exit code (§J elaborates the rationale: failing a green CI run over an unrelated Docker-daemon flake would produce false negatives).
- **What may appear in logs:** container/database/bucket names (already non-sensitive by construction, §13), port numbers, migration file names/counts, test pass/fail counts, timestamps. **Never:** the full `DATABASE_URL` (contains a generated password), `MINIO_SECRET_KEY`, or the value of any generated credential — only the *fact* that a fresh credential was generated.

## 16. Local Windows execution design

A future (not-yet-implemented) `scripts/test-db-up.ps1` / `scripts/test-db-down.ps1` pair, invoked manually by a developer or from a pre-test npm script, performs steps 1-6 of §14 using PowerShell-native `docker run`/`docker port`/polling constructs, writing the resolved `DATABASE_URL`/`MINIO_*` values to the invoking shell's environment (e.g., via a small `.env.local.generated` file the developer sources, or directly exported for the current PowerShell session) — never to a committed file. A local-developer-convenience variant (Option B from §9/§11, a long-lived shared container reused across runs via `CREATE DATABASE`/`CreateBucket` per invocation) may optionally be offered as a faster inner-loop alternative, explicitly documented as **not** the CI model and **not** exempt from the same naming/label/sweeper contract.

## 17. GitHub Actions execution design

A future (not-yet-implemented) workflow (new file, or a new job appended to a copy of the existing pattern — this task creates no workflow file) would declare `services: { postgres: { image: 'postgres:16-alpine', env: {...generated...}, ports: ['5432'], options: '--health-cmd pg_isready --health-interval 5s --health-timeout 5s --health-retries 12' } }` (and an equivalent `minio` service only for the one job that needs it, with a manual health-check step since MinIO has no first-class `--health-cmd` equivalent as simple as `pg_isready`), following the existing `windows-bridge-pr.yml`'s own conventions: pinned third-party actions by commit SHA (already the pattern for `actions/checkout`/`actions/setup-node`), a `concurrency: { group: …, cancel-in-progress: true }` block, an explicit `timeout-minutes` (recommend 20-30, well above any historically-observed disposable-Postgres test duration, well below GH's loose 360-minute default), and `path`-triggered scoping analogous to the existing workflow's own `paths:` filter (this design does not decide the exact trigger paths — that is a P1/implementation-time decision informed by whichever script matrix P1 finalizes, §26).

## 18. Network/provider isolation

Every existing external-provider touchpoint (Meta WhatsApp Cloud, Instagram Graph API, Evolution WhatsApp, SMS, Email/SMTP, Gemini/AI) is already fully stubbed or environment-gated at the test level, per F1-002-P2's `externalDependencyAssessment` — **zero live provider calls were found anywhere in the 105-file backend or 9-file frontend suite**, a finding this task did not need to re-derive since it falls outside this task's own targeted CodeGraph roots, but which this design's network-isolation posture explicitly relies on holding. This design recommends (not implements) a **new** defense-in-depth control not present today: a shared test-bootstrap module that installs a global `fetch`/`undici` dispatcher override during any disposable-runtime-backed test run, allow-listing only the resolved `DATABASE_URL` host and `MINIO_ENDPOINT` host (plus `127.0.0.1`/`localhost` generally) and throwing on any other outbound HTTP(S) attempt — this would convert "we believe every provider call is stubbed" into "a live call is structurally impossible during this run," closing the residual risk the `messagesConsentGate.test.ts` UNKNOWN finding represents (§26). At the CI-runner level, this design further recommends (not implements) restricting the runner's own network egress to the npm registry, GitHub, and loopback only, for any job that runs disposable-Postgres/MinIO-backed tests — belt-and-suspenders against a future test regression reintroducing a live call.

## 19. Secret/log safety

No secret value (generated Postgres password, generated MinIO secret key, any `DATABASE_URL` containing a password) may appear in a log line, container label, or committed artifact — only the *fact* that a fresh, random, test-only credential was generated. This document itself contains **zero** real credential values, **zero** real `DATABASE_URL` values, and **zero** production hostnames beyond the ones already publicly documented in `server/.env.example` (`app.noramedi.com`, cited only to describe *what the production-URL guard, §20, must detect and reject* — never as a target this design connects to).

## 20. R-070 and migration rollback boundary

Restated exactly, not narrowed: standard `prisma migrate deploy` is **forward-only** and is **not** rollback tooling. This design's default profiles (§21, profiles 1-4) never mutate `_prisma_migrations` directly and never perform a physical schema rollback. Profile 5 (destructive rollback rehearsal) is explicitly separate, opt-in, non-default, and mirrors F0-011-P2's own already-completed rehearsal methodology — it does not introduce any new automated rollback tool, does not recommend `DELETE FROM _prisma_migrations` as anything other than the emergency-only, unsupported technique R-070 already documents, and does not close R-070. **R-070 remains OPEN.** This design's own eventual implementation must not be read, cited, or represented as resolving R-070's underlying tooling gap (no drift-detection between `_prisma_migrations` and true schema state, no documented reconciliation runbook) under any circumstance.

## 21. Security impact

This design **adds** two new controls beyond today's ad hoc practice: (1) a fail-closed production-URL detector for `DATABASE_URL`/`MINIO_ENDPOINT` before any provisioning command runs (§4 Q10, §J), and (2) a recommended network-egress guard (§18) — both net security improvements, neither implemented by this task. It **reduces** reliance on the test file's own hardcoded `reviewminio`/`reviewminiosecret` MinIO credentials for anything beyond manual/ad hoc local use, in favor of per-run-generated credentials. It introduces **no** change to any application authorization/authentication code path, no new production access, and no new external network dependency (MinIO/Postgres remain local/disposable).

## 22. Tenant-isolation impact

None — this design changes only the *infrastructure hosting* test execution, not fixture generation, authorization logic, or scope-filtering code. Every fixture-builder this task read (`dbVerificationHarness.ts`'s `createClinicFixtureSet`/`createStaffUser`/`createTestPatient`) continues to generate synthetic, UUID-suffixed, multi-org/multi-clinic fixtures exactly as today; this design does not touch that code.

## 23. KVKK/privacy impact

None — no real patient data is introduced, referenced, or required by this design. Disposable databases and buckets are transient and fully destroyed per run (§15). This design explicitly reinforces, as a hard rule feeding the fail-safe contract, that any fixture producing a non-synthetic-looking value (a real name, a real phone number, a non-`@example.invalid`-style email) inside a disposable-runtime-backed test would be a defect in that test, not an acceptable input to this provisioning design — consistent with every fixture this task observed (`test-staff-<suffix>@example.invalid`, `+9055500<suffix>` phone numbers, generic `Test`/`Synthetic Patient-<suffix>` names).

A future F1-003-P2 implementation PR (new scripts, new/modified workflow file, new labels/conventions) is revertible via a normal single-commit or PR-level `git revert` — no database, storage, or production rollback is implied, because no disposable resource this design describes is ever durable by design. Disabling a misbehaving CI job (removing its trigger or the job block) is sufficient to stop it; nothing is "left behind" at the infrastructure level since every container is ephemeral and unvolumed.
